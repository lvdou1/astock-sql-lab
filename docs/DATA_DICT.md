# 数据字典与设计说明

## 1. 字段字典

### dim_industry（行业维度，30 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `industry_code` | VARCHAR | 主键，申万行业代码，如 `801080` |
| `industry_name` | VARCHAR | 申万一级行业名（电子、医药生物、银行…） |
| `industry_level` | VARCHAR | 自定义大类：消费/金融/医药/科技/制造/周期/公用 |

申万一级共 31 个行业，中证800 成分股覆盖其中 30 个（缺"综合"之外的个别小类）。

`industry_level` 存在的意义：做跨行业横向比较时，31 个分类太细，且部分行业在样本内只有 3-5 只；归到 7 大类后每组样本才够看。**更重要的是它能表达业务规则**——异常评分里"排除金融"就是靠 `industry_level <> '金融'` 这一句，而不是逐个列举银行和非银金融。

### dim_stock（股票维度，799 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `stock_code` | VARCHAR | 主键，**6 位字符串**，如 `000001` |
| `stock_name` | VARCHAR | 证券简称 |
| `industry_code` | VARCHAR | 外键 → `dim_industry` |
| `board` | VARCHAR | 主板 / 创业板 / 科创板 |
| `index_membership` | VARCHAR | 沪深300 / 中证500 |
| `is_st` | BOOLEAN | 是否 ST（本样本池无 ST 股，字段保留） |

**为什么 `stock_code` 是 VARCHAR 而不是 INT**：`000001` 存成整数会变成 `1`，前导零丢失，之后再补不回来。CSV 装载时若不显式声明类型，DuckDB 会自动推断成 BIGINT——这是 CSV 入库最常见的坑。

**为什么要 `board`**：涨跌停幅度按板块不同（主板 10%、创业板/科创板 20%、新股前 5 日不设限）。做异常涨跌幅校验时不区分板块，正常波动会被误判成异常。

**为什么要 `index_membership`**：沪深300 与中证500 在这五年（2022-2026）的表现差异明显（收益中位数 +10.17% vs -2.08%），这个字段让"大盘 vs 中盘"的对比变成一句 `GROUP BY`。

### fact_daily_quote（日行情事实表，916,544 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `stock_code` | VARCHAR | 外键 → `dim_stock` |
| `trade_date` | DATE | 交易日 |
| `open` / `high` / `low` / `close` | DOUBLE | **后复权**价格 |
| `volume` | BIGINT | 成交量（股） |
| `amount` | DOUBLE | 成交额（元） |
| `turnover_rate` | DOUBLE | 换手率，% |

主键 `(stock_code, trade_date)`。

**为什么用后复权**：前复权会在每次分红后重算全部历史价格，同一份查询今天跑和明天跑结果不同，不可复现。后复权只影响当前价格、不改历史，适合收益与回撤计算。

**代价**：`close` 不能直接和行情软件报价对比。例如贵州茅台 2022-01-04 的 `close` 是 12,092.5，当天名义收盘价是 2,051.23 元——这是复权因子累积的结果（5.9 倍）。算收益率百分数是对的，引用绝对价格会闹笑话。

### fact_financial（财务事实表，15,113 行）

| 字段 | 类型 | 说明 | 缺失情况 |
|---|---|---|---|
| `stock_code` | VARCHAR | 外键 | — |
| `report_date` | DATE | 报告期末（非公告日） | — |
| `revenue_yoy` | DOUBLE | 营业收入同比 % | 金融业部分缺失 |
| `profit_yoy` | DOUBLE | 净利润同比 % | 少量缺失 |
| `net_margin` | DOUBLE | 销售净利率 % | 金融业缺失 |
| `gross_margin` | DOUBLE | 主营业务利润率 % | 金融业缺失 |
| `roe` | DOUBLE | 净资产收益率 % | — |
| `roa` | DOUBLE | 总资产净利润率 % | — |
| `eps` | DOUBLE | 摊薄每股收益（元） | — |
| `bps` | DOUBLE | 每股净资产（元） | — |
| `ocf_ps` | DOUBLE | 每股经营性现金流（元） | — |
| `ar_days` | DOUBLE | 应收账款周转天数 | **银行 100% 缺失；非银有值但不可比** |
| `inv_days` | DOUBLE | 存货周转天数 | **银行 100% 缺失** |

主键 `(stock_code, report_date)`，19 期（2022Q1 ~ 2026Q3）。

## 2. 三个关键口径问题

### 2.1 财务数据是「累计口径」，不能直接比

A 股财报的 Q2 是「1-6 月累计」，Q3 是「1-9 月累计」，Q4 是全年。所以：

```sql
-- 错的：拿 Q3 和 Q2 比，比的是 9 个月 vs 6 个月
WHERE report_date >= '2026-06-30'

-- 对的：同报告期对齐，2026Q3 vs 2025Q3
JOIN fact_financial prev
  ON MONTH(cur.report_date) = MONTH(prev.report_date)
 AND YEAR(cur.report_date)  = YEAR(prev.report_date) + 1
```

`04` 和 `05` 都用了这个写法。**只写 `date - interval '1 year'` 是不够的**：财务表里只要有一个期间缺失，简单相减就会错位；用 MONTH/DAY 对齐能保证只连到真正同期的记录。

推论：`revenue_yoy` 这类同比增速可以直接用（数据源已算好），但「环比」在本数据里**做不出来**，需要先还原单季值（Q2单季 = Q2累计 - Q1累计）。

### 2.2 累计口径还有一个副作用：现金流天然为负

一季度报的经营现金流常为负（备货、发年终奖、收账周期），这不是问题。本数据里一季报约三成 `ocf_ps < 0`。

所以 `05` 的 R4 规则写的是**「由正转负」**而不是「为负」：

```sql
CASE WHEN ocf_ps < 0 AND prev_ocf_ps > 0 AND profit_yoy > 0 THEN 1 ELSE 0 END
```

如果写成 `ocf_ps < 0`，大量正常的一季报会被误判。

### 2.3 金融业有"应收账款"，但和制造业不是一回事

银行没有应收/存货科目，`ar_days`/`inv_days` 100% 是 NULL，这个好识别。

**真正的坑是非银金融（券商、保险、多元金融）**：它们有应收账款科目，但构成完全不同——券商的应收主要是客户保证金、清算款、代买卖证券款，用制造业的「应收账款 / 营业收入 × 365」去算，分母口径根本不对。

实测结果：湘财股份的应收周转天数算出来是 **8,910 天（24 年）**，国投资本 4,097 天。这不是经营异常，是公式用错了场景。

如果异常评分只按 `ar_days IS NOT NULL` 过滤，湘财股份会被评成"高风险"——**这是本项目最典型的一次误报，也是必须整类排除金融业的原因**：

```sql
JOIN dim_industry i ON i.industry_code = st.industry_code
WHERE i.industry_level <> '金融'      -- 不是 <> '银行'，是整类
```

## 3. 为什么保留金融股

既然口径对不上，为什么不直接从股票池里删掉？

因为**"发现某类标的不能纳入同一套指标"本身就是分析能力**。删掉等于把问题藏起来，保留并在 SQL 里显式排除，反而是能在面试里讲十分钟的细节。

同理保留的还有 `is_st` 字段（虽然中证800 里没有 ST 股）——字段在，口径在，只是样本里暂时为空。

## 4. 数据质量的两个特殊规则

### 4.1 新股上市前 5 个交易日不设涨跌幅限制

注册制下，科创板/创业板新股上市前 5 日不设涨跌幅。实测中合合信息（688615）上市第 3-5 个交易日出现 +96%、+42.9%、-50% 的单日波动，看着像脏数据，其实是规则。

所以 `06` 把极端涨跌幅拆成两行统计：

- `rn <= 5`（上市前 5 个交易日）→ 标记为「规则内，正常」
- `rn > 5` → 标记为「需核查」，本项目只剩 1 条（中孚实业重组复牌）

### 4.2 停牌与上市时间造成交易日不足

有 175 只股票的交易日少于全市场，原因包括停牌、退市整理、上市较晚。**这不是数据错误**，但做"某日横截面"分析时要注意：直接用 `trade_date = '2026-11-16'` 取全市场，会漏掉当天停牌的标的。

## 5. 为什么事实表用 Parquet

| | CSV | Parquet |
|---|---|---|
| 91 万行体积 | 约 25 MB | **18.4 MB**（ZSTD） |
| 类型 | 无，需手写 CAST | 自带 schema |
| 读取 | 全表解析 | 列裁剪，只读用到的列 |

`02_load.sql` 里就一行：

```sql
INSERT INTO fact_daily_quote SELECT * FROM read_parquet('data/fact_daily_quote.parquet');
```

维度表反过来用 CSV——1 万行以内、人要能直接用 Excel 打开看，CSV 更合适。

## 6. 数据集规模与扩展

当前 799 只股票、91.6 万行日线、1.5 万期财报，建库约 4 秒、含 6 个查询的全流程约 6 秒。

这个规模的取舍：**大到统计有意义（30 个行业，头部行业 60-104 只），小到 clone 下来只有 18 MB、几秒能跑完**。

想继续扩展：

1. 全市场（约 5,400 只 × 10 年 ≈ 2,000 万行）：改 `scripts/fetch_data.py` 的 `INDEX_CODES`，改为从 `ak.stock_info_a_code_name()` 拉全量代码。取数约 1.3 小时（6 并发），Parquet 会到 400 MB 左右，不建议直接放进 Git。
2. 想抓财务造假，样本应该往**中小盘**走（中证1000、创业板指），而不是继续加蓝筹——本项目 799 只里只有 1 只高风险，本身就说明蓝筹池的财报质量整体较好。
