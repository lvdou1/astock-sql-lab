# 数据字典与设计说明

## 1. 字段字典

### dim_industry（行业维度，10 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `industry_code` | VARCHAR | 主键，`SW01`~`SW10` 编号 |
| `industry_name` | VARCHAR | 申万一级行业名（食品饮料、银行、医药生物…） |
| `industry_level` | VARCHAR | 自定义一级归类：消费/金融/医药/科技/制造/周期 |

`industry_level` 存在的意义：申万一级切得太细（银行、有色金属各自只有 1-4 个样本），做横向对比时样本不足。归类到 6 个大类后，同组样本量才够看。

### dim_stock（股票维度，22 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `stock_code` | VARCHAR | 主键，**6 位字符串**，如 `000001` |
| `stock_name` | VARCHAR | 证券简称 |
| `industry_code` | VARCHAR | 外键 → `dim_industry` |
| `board` | VARCHAR | 主板 / 创业板 |
| `is_st` | BOOLEAN | 是否 ST |

**为什么 `stock_code` 是 VARCHAR 而不是 INT**：`000001` 存成整数会变成 `1`，前导零丢失，之后再怎么补都补不回来。CSV 装载时若不显式声明列类型，DuckDB 会自动推断成 BIGINT——这是 CSV 入库最常见的坑，所以 `02_load.sql` 里每个字段都手写了类型。

**为什么要 `board`**：创业板涨跌停是 20%，主板是 10%。做异常涨跌幅校验时如果不区分板块，创业板正常波动会被误判成异常。

### fact_daily_quote（日行情事实表，25,914 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `stock_code` | VARCHAR | 外键 → `dim_stock` |
| `trade_date` | DATE | 交易日 |
| `open` / `high` / `low` / `close` | DOUBLE | **后复权**价格 |
| `volume` | BIGINT | 成交量（股） |
| `amount` | DOUBLE | 成交额（元） |
| `turnover_rate` | DOUBLE | 换手率，% |

主键 `(stock_code, trade_date)`。

**为什么用后复权**：前复权会在每次分红后重算全部历史价格，同一份查询今天跑和明天跑结果不同，不可复现。后复权只影响当前价格、不改历史，适合做收益与回撤计算。

**代价**：`close` 不能直接和行情软件上的报价对比。比如贵州茅台 2022-01-04 的 `close` 是 12,092.5，而当天名义收盘价是 2,051.23 元——这是复权因子累积的结果（5.9 倍）。做收益率时百分数是对的，绝对价格不要引用。

### fact_financial（财务事实表，418 行）

| 字段 | 类型 | 说明 | 缺失情况 |
|---|---|---|---|
| `stock_code` | VARCHAR | 外键 | — |
| `report_date` | DATE | 报告期末（非公告日） | — |
| `revenue_yoy` | DOUBLE | 营业收入同比 % | 银行缺失 |
| `profit_yoy` | DOUBLE | 净利润同比 % | 少量缺失 |
| `net_margin` | DOUBLE | 销售净利率 % | 银行缺失 |
| `gross_margin` | DOUBLE | 主营业务利润率 % | 银行缺失 |
| `roe` | DOUBLE | 净资产收益率 % | — |
| `roa` | DOUBLE | 总资产净利润率 % | — |
| `eps` | DOUBLE | 摊薄每股收益（元） | — |
| `bps` | DOUBLE | 每股净资产（元） | — |
| `ocf_ps` | DOUBLE | 每股经营性现金流（元） | — |
| `ar_days` | DOUBLE | 应收账款周转天数 | **银行 100% 缺失** |
| `inv_days` | DOUBLE | 存货周转天数 | **银行 100% 缺失** |

主键 `(stock_code, report_date)`，19 期（2022Q1 ~ 2026Q3）。

## 2. 三个关键口径问题

### 2.1 财务数据是「累计口径」，不能直接比

A 股财报的 Q2 是「1-6 月累计」，Q3 是「1-9 月累计」，Q4 是全年。所以：

```sql
-- 错的：拿 Q3 和 Q2 比，比的是 9 个月 vs 6 个月
WHERE report_date >= '2026-06-30'

-- 对的：同报告期对齐，2026Q3 vs 2025Q3
JOIN fact_financial prev
  ON MONTH(cur.report_date) = MONTH(prev.report_date)
 AND YEAR(cur.report_date)  = YEAR(prev.report_date) + 1
```

`04` 和 `05` 两个查询都用了这个写法。**只写 `date - interval '1 year'` 是不够的**，因为财务表里只要有一个期间缺失，简单相减就会错位；用 MONTH/DAY 对齐能保证只连到真正同期的记录。

推论：`revenue_yoy` 这类同比增速可以直接用（数据源已算好），但「环比」在本数据里**做不出来**，需要先还原单季值（Q2单季 = Q2累计 - Q1累计）。

### 2.2 累计口径还有一个副作用：现金流天然为负

一季度报的经营现金流常为负（备货、发年终奖、收账周期），这不是问题。本项目 110 条一季报里有 31 条 `ocf_ps < 0`，占 28%。

所以 `05` 的 R4 规则写的是**「由正转负」**而不是「为负」：

```sql
CASE WHEN ocf_ps < 0 AND prev_ocf_ps > 0 AND profit_yoy > 0 THEN 1 ELSE 0 END
```

如果写成 `ocf_ps < 0`，近三分之一的一季报会被误判。

### 2.3 银行股没有应收/存货科目

银行的报表结构是「贷款/存款/利息收入」，压根没有「应收账款周转天数」「存货周转天数」。所以这 4 家银行的这两列 100% 是 NULL（`06` 查询里有 79 条记录）。

**这是口径差异，不是脏数据。** 但它会污染所有统计：如果不加 `WHERE ar_days IS NOT NULL`，算出来的平均周转天数会偏低，因为银行被当成"周转极快"混进去了。

`05` 的 `WHERE ar_days IS NOT NULL AND inv_days IS NOT NULL` 就是为这个加的。

## 3. 为什么保留银行股

既然口径对不上，为什么不直接删掉？

因为**"发现某类标的不能纳入同一套指标"本身就是分析能力**。删掉等于把问题藏起来；保留并在 SQL 里显式排除，反而是能在面试里讲十分钟的细节。

同理保留的还有 ST康美——它历史上因财务造假被处罚，是验证异常规则最好的人肉样本。只不过它的造假期（2018-2020）在数据窗口（2022 起）之外，所以本项目拿不到它的高分，这一点在 README 的已知限制里写明了。

## 4. 数据集规模与扩展

当前 22 只股票、2.6 万行日线、418 期财报，从建库到 6 个查询全部出结果不到 1 秒。这个规模的设计意图是**让人愿意真的跑一遍**。

如果想扩到全市场（约 5,000 只 × 10 年 ≈ 1,200 万行）：

1. 改 `scripts/fetch_data.py` 里的 `UNIVERSE`，或从 `ak.stock_info_a_code_name()` 拉全量代码
2. 取数会变慢（单只约 1.5 秒，全市场约 2 小时），建议加断点续传
3. 索引才会开始有意义——`03_index.sql` 里注释掉的对比实验值得重做一次

## 5. 数据来源与免责

- 行情：腾讯财经公开接口，后复权
- 财务：新浪财经公开接口，比率口径
- 行业分类：申万一级，手工归类，**可能与官方最新分类有偏差**

数据仅用于技术学习与项目展示，不构成投资建议，也不保证准确性。用于任何实际决策前请以 Wind / iFinD / 交易所公告为准。
